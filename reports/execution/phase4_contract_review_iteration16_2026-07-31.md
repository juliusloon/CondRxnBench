## Remaining blocking findings

### P0-1 — `verify_metrics_v0_1_toy.py` is not yet a contract verifier

The command exits successfully, but several checks assert a hard-coded fact or
the library’s default behavior rather than the expected value in the versioned
fixture/contract:

- Lines 40–42 only confirm the fixture strings and that a helper returns its
  own literal; they do not call an empty-input or missing-prediction metric
  path and compare its result to the fixture.
- Line 45 passes whenever scikit-learn returns `0.0` for constant truth:
  `assert r2_score(...) == 0.0 or not_supported_if(True)`.  The frozen contract
  instead requires `not_supported_with_reason`; `constant_truth.expected_r2`
  is never consumed.
- The `corr` helper (lines 25–28) computes only Spearman, despite the contract
  requiring both delta Pearson and Spearman.  Its chosen two-point example
  cannot distinguish their implementations.
- No executable assertion covers direction accuracy/macro-F1; numeric expected
  MAE/RMSE, Pearson/Spearman, AUPRC/AUROC/F1, NDCG, top-k recall, factor-wise
  sensitivity, mean-over-groups variance ratio, or regret are not supplied by
  the fixture and compared to a contract implementation.  Several current
  assertions use inline numbers rather than versioned expected fixture values.
- The zero-denominator sensitivity case merely reads its expected string (line
  64), not the formula’s guarded execution; `regret` and top-k hit are likewise
  reduced to static arithmetic/string checks.

This fails the goal’s requirement that **each metric** have analytically
verifiable toy cases, boundary tests, and negative controls.  A script which
passes while contradicting the declared R2 edge behavior cannot gate later
evaluation.

**Required minimal repair:** create metric functions that implement the
contract and make the verifier load every expected input/output from the
fixture.  Give distinct numerical expected values for all metric families and
guarded edge states, including Pearson versus Spearman, and assert the exact
`not_supported`/`reject_input` reason code.  Add source/group/factor-labelled
fixtures for macro aggregation, factor-wise sensitivity, and variance ratio.

### P0-2 — top-level metric registry still contradicts the task binding

Although `Task2_delta_yield.metrics` no longer includes
`within_group_variance_ratio`, contract line 23 still places it in
`metrics.pair`.  The same line defines the formula over `predicted_yield`,
which belongs to Task 1.  Unless the top-level registry is explicitly labelled
non-authoritative, a later evaluator can reasonably select it for direct pair
prediction and recreate the incompatibility just fixed.

**Required minimal repair:** move `within_group_variance_ratio` from
`metrics.pair` to the absolute/Task 1 registry (or replace the top-level lists
with a strict derivation of the `tasks.*.metrics` arrays), then add a verifier
assertion that no task is assigned a metric incompatible with its prediction
interface.
